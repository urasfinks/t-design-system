# Обязательные правила работы с TDS

Перед любыми изменениями прочитайте этот файл, `DESIGN.md` и
`docs/component-standard.md`. Затем изучите существующую реализацию затронутого
семейства и его проверки. Эти правила действуют для исходников, runtime и каталога.
Прямые требования пользователя имеют приоритет; противоречия с документацией
нужно явно обозначить и устранить в рамках задачи.

## 1. Один источник каждого общего решения

- Общее правило принадлежит токенам, темам, base или общему движку семейства.
  Компоненты подключают его и задают только необходимые параметры и отличия.
- Перед исправлением найдите ВСЕ потребители общего правила. Исправление меню
  не завершено, если аналогичный listbox продолжает использовать отдельную реализацию.
- Не копируйте декларации общего решения между компонентами. Не добавляйте
  поздние патчи, усиление специфичности или `!important` для обхода владельца правила.
- Существующие отличия не считайте автоматически необходимыми: проверьте их смысл.
  Осмысленные исключения документируйте рядом с реализацией и проверяйте отдельно.

## 2. Каскад должен работать на практике

- «Всё наследуемо» означает единый источник и распространение общих изменений.
  `gap`, `padding`, `border` и `display` буквально не наследуются: одинаковая
  компоновка подключается общим миксином к каждому соответствующему контейнеру.
- Токены меняются у своего владельца. Не закрепляйте их текущие значения числами
  в компонентах и не перекрывайте общие настройки без документированной причины.
- Вложенные группы проверяются наравне с внешними контейнерами.
- Проверяйте вычисленные стили и фактическую геометрию в браузере. Наличие
  одинаковых классов или миксинов ещё не доказывает правильный результат.
- При изменении общего правила проверьте его распространение: изменение токена
  должно влиять на всех потребителей без отдельных исправлений.

## 3. Сохраняйте визуальный язык

- Используйте существующие токены типографики, цвета, размеров и интервалов.
  Не вводите новые значения, если задача решается имеющимися ролями.
- Внутренние строки и выбранные элементы остаются плоскими. Тень отделяет
  всплывающую или действительно приподнятую поверхность. Кольцо фокуса и
  контрастная обводка не являются декоративной тенью и должны сохраняться.
- Иконка внутри бейджа получает размер из TDS; потребитель не подгоняет её вручную.
  Иконка и интерактивность не должны случайно увеличивать высоту бейджа.
- Состояние задаётся семантикой HTML/ARIA и общим движком состояний.
  Не заменяйте button/link стилизованным div; сохраняйте клавиатуру и видимый фокус.

## 4. Приложение и каталог используют систему

- Исправляйте библиотеку в `src`, затем собирайте `dist`. Не редактируйте
  сгенерированный CSS вручную и не копируйте реализацию в приложение.
- Приложение компонует публичные компоненты и утилиты TDS без собственного CSS,
  inline-стилей и переопределений токенов. Недостающий общий вариант добавляется в TDS.
- Каталог демонстрирует настоящие компоненты. Его CSS отвечает за расположение
  примеров, а не за отдельное оформление их внутренностей.
- Сохраняйте структуру соседних разделов: пример → правило применения → HTML.
  Подписи классов: `<code translate="no" class="class-tag">…</code>`.
- Не удаляйте примеры, состояния и публичные классы ради упрощения задачи.
  Не дублируйте справочник компонента в нескольких местах; используйте ссылки.

## 5. Проверки до заявления о готовности

- Для исправления ошибки сначала воспроизведите её. Для общего правила проверка
  должна охватывать разные потребители и вложенные группы, а не только скриншот.
- Запустите `npm test` в TDS. Для визуального изменения выполните относящиеся
  к нему браузерные проверки в Chromium и WebKit, проверьте светлую, тёмную и
  iOS-тёмную темы, а также фактический вид затронутого примера.
- При изменении строк выбора используйте `tests/option-spacing.browser.mjs` и
  `tests/option-selection.browser.mjs` (для WebKit добавьте `--webkit`).
- При изменении приложения выполните его `npm run check:tds` и подходящие проверки.
- Проверьте diff: нет случайных удалений, локальных заплаток и несвязанных изменений.
- Сообщайте только реально выполненные проверки. Если что-то не проверено или
  заблокировано, прямо укажите это; не объявляйте всю систему проверенной по одному примеру.
