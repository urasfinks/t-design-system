# Полная реализация компонентов по архиву 21st.dev

Дата: 27.10.2026. Статус: на согласовании.

## Намерение

Реализовать в T Design System все **компоненты** из спецификаций
`references/21st-dev-1000/images/*/components.md` (17 папок). Секции лендингов и
композиции — готовые куски страниц, собранные из существующих классов, — в работу не
входят: это не компоненты.
Владелец хочет сильный визуал и сбалансированный каскад: каждое значение живёт на своём
уровне, общее не дублируется, все компоненты видны в одном каталоге `docs/index.html`.

Работа идёт без участия владельца между волнами и без коммитов; владелец один раз
коммитит итог, если он ему понравится. Поэтому работа должна быть восстановима после
сбоя исполнителя в любой момент: место остановки определяется по файлам проекта, а не по
памяти исполнителя или истории git.

## Текущее состояние

- Спецификации: 192 описания. Статусы: `composition` 86, `new` 48, `extend` 36,
  `existing` 22. Приоритеты: P0 42, P1 90, P2 60.
- Уже реализовано (волна P0): A1, A4, B2, B5, B7, B14, C1, C6, D1 (части `__cell-main`,
  `--compact`, `--stack`, `--caption-bottom`), D2, D4, F2, F3, F11 (`__description`),
  F12, FT1, M1, M2, M5, M6, M13, N1 (`--underline`), N4, N9, N12. Есть живой экран
  `docs/workspace.html`, тест `tests/workspace.browser.mjs`, примеры в каталоге,
  раздел «Меню действий».
- Ядро: tokens → themes → base (с `components/control-states`) → components →
  utilities → visibility. Компоненты задают параметры (`--control-idle-bg`,
  `--control-hover-bg`, `--control-hover-filter`, `--control-paint-duration`), общий
  движок даёт hover, переход и нажатие. Поиск и группа полей используют общий миксин
  `components/field-surface`.
- Эталон: `tests/baseline-compatibility.browser.mjs` сейчас сравнивает всю страницу
  каталога и проверяет контрольную сумму `docs/index.html`, поэтому любое добавление
  примеров требует обновления эталона.
- Тестовая среда исполнителя: Chromium есть, WebKit нет. Юнит-тесты и сборка идут и на
  машине владельца.

## Цели

1. Каждая из 110 компонентных спецификаций реализована и показана в каталоге:
   - `new` и `extend` (84) — новый CSS в модуле-владельце, пример, браузерный тест;
   - `existing` (22) — пример в каталоге (если ещё нет) и проверка состояний;
   - четыре композиции, которые вводят новый класс компонента: C16 `.tg-grid--bento`,
     M9 `.tg-stepper--vertical`, M10 `.tg-timeline--horizontal`, S2 `.tg-divider--label`.
   Остальные 82 композиции (включая все секции лендингов) в работу не входят.
2. Каскад сбалансирован: повторяющиеся механизмы выделены в общие движки, компоненты
   настраивают их параметрами.
3. Сильный визуал: результат проходит планку impeccable (craft floor), Emil design
   engineering и DESIGN.md во всех трёх темах на 320, 390 и 1440 px.
4. Восстановимость: скрипт сверки по каждой спецификации в работе показывает, что готово.

## Не цели

- Секции лендингов (герои, возможности, тарифы, отзывы, галереи, призывы к действию,
  экраны входа, подвалы) и прочие композиции из готовых классов.
- Пиксельное копирование превью 21st.dev, их палитр, шрифтов и бизнес-логики.
- Runtime-библиотека поведения. TDS даёт стили и ARIA-контракт; поведение примеров
  живёт в `docs/*.js` как образец для приложения (как сейчас `catalog-demos.js`).
- Изменение внешнего вида или API существующих компонентов.
- Коммиты и операции git со стороны исполнителя.

## Анти-цели (провал, даже если «работает»)

- Существующий компонент выглядит или ведёт себя иначе, чем до работы.
- Компонент получает собственный набор правил, повторяющий другой компонент.
- Новый компонент копирует hover, переход, фокус или поверхность вместо общего движка.
- Новые цвета или `color-mix()` вне десяти разрешённых токенов палитры.
- Декоративный эффект становится обязательным для базового интерфейса.
- Каталог разваливается на отдельные страницы.
- После сбоя невозможно понять, какие спецификации готовы.

## Ограничения

- Каскад и правила `docs/component-standard.md`, DESIGN.md, README: префикс `.tg-*`,
  `@layer tds.components`, без `!important` и ID-селекторов, анимируются только
  `transform` и `opacity` (кроме явно разрешённых в DESIGN.md случаев), touch ≥ 44 px,
  видимый фокус, reduced motion, RTL, текст 200%.
- Существующие тесты остаются зелёными; меняются только ожидания, которые закрепляли
  прежний состав каталога (число разделов, примеров), с пояснением в изменении.
- Независимый SCSS-импорт каждого модуля продолжает компилироваться.
- В каталоге сохраняются правила DESIGN.md: порядок «пример → правило → HTML», правило
  в одно-два предложения, у полей примеров `name`, у кода `translate="no"`.
- Текст интерфейса и примеров на русском, данные примеров помечены как пример.

## Рассмотренные подходы

1. **По папкам.** Простой учёт, но компоненты разных папок зависят друг от друга
   (календарь, всплывающий слой, выбор), общее дублируется или переделывается. Отброшен.
2. **Волнами по зависимостям.** Естественное переиспользование и ранний видимый
   результат; риск, что общие механизмы выделяются поздно.
3. **Сначала общие движки, потом компоненты.** Максимально сбалансированный каскад,
   но первая волна почти без видимого результата.

**Выбрано владельцем: соединение 3 и 2.** Волна 0 выделяет общие движки, каждый сразу
проверяется на одном-двух компонентах; дальше волны по зависимостям; эффекты в конце.

## Решения владельца

- Реализуются все компоненты; секции лендингов и композиции не нужны — это не компоненты.
- Строгий каскад и полное переиспользование.
- Все компоненты в одном каталоге `docs/index.html`.
- Эталон больше не обновляется каждую волну: тест проверяет только неизменность
  прежнего содержимого.
- Исполнитель проходит все волны подряд без коммитов; владелец коммитит один раз в конце.
- Критерий приёмки: сильный визуал и сбалансированный каскад.

## Как строится

### 1. Эталон: проверять только прежнее

Первая задача — перестроить `tests/baseline-compatibility.browser.mjs`:

- В `tests/fixtures/cascade-baseline/` сохраняется копия текущей разметки каталога
  (`index.html`) вместе с текущими CSS эталона.
- Тест рендерит **сохранённую** разметку с CSS эталона и с текущим CSS и требует
  совпадения пикселей и вычисленных стилей (как сейчас: 3 темы × 3 ширины × 3 акцента).
- Отдельная проверка требует, чтобы каждый раздел и каждый пример сохранённой разметки
  присутствовал в текущем каталоге с тем же содержимым (по `id` разделов и тексту правил).
- Проверка контрольной суммы `docs/index.html` убирается; суммы файлов эталона остаются.
- Существующая проверка «нет локальных акцентов в разметке» сохраняется.

### 2. Учёт и восстановление

- Реестр `references/21st-dev-1000/implementation.json`: для каждого ID спецификации —
  статус (`todo`, `done`), список публичных классов, которые должны быть в
  `dist/t-design-system.css`, и файл теста.
- В каталоге у примера, реализующего спецификацию, атрибут `data-spec="B8 F15"` на
  `.example-body`. Атрибут не влияет на стили.
- Скрипт `scripts/verify-implementation.mjs` по каждой спецификации в работе проверяет:
  классы есть в собранном CSS; в каталоге есть пример с её ID; тест упоминает ID;
  статус в реестре. Печатает сводку по волнам и первую незавершённую спецификацию.
  Выход 0 только когда готовы все 110 спецификаций в работе.
- План (writing-plans) отмечает шаги галочками сразу после выполнения. После сбоя:
  открыть план, запустить скрипт сверки, продолжить с первой незавершённой задачи.

### 3. Общие движки (волна 0)

Каждый движок — миксин или параметризованный модуль на уровне владельца, как
`field-surface`. Существующие компоненты переводятся на движок только если вычисленные
стили не меняются (проверяет эталон).

- **Всплывающий слой** (`components/floating`): поверхность (фон, рамка, радиус, тень
  плавающего слоя), появление от триггера и уход (`opacity` + `scale`, `@starting-style`,
  быстрее на выходе, мгновенно с клавиатуры), позиционирование через CSS anchor с
  документированными параметрами хоста, нижний лист на узком сенсорном экране.
  Первые потребители: меню (перевод без изменения вида), подсказка B15.
- **Строка-вариант** (`components/option`): геометрия строки 44 px, ведущая иконка,
  текст и мета, замыкающий элемент, подсветка активной строки, отметка выбора маской.
  Потребители: пункты меню, listbox, палитра команд, боковая панель, оглавление.
- **Выбранное состояние**: один набор параметров для «выбрано» (мягкий акцент) и
  «нажато» (заливка) — уже частично общий для `.tg-toggle` и `.tg-btn--stacked`.
  Потребители: сегменты B8, карточки выбора F14, чипы, вкладки.
- **Дорожка прокрутки** (`components/track`): горизонтальная или вертикальная прокрутка
  со snap, края с затуханием (M22), кнопки и индикаторы. Потребители: карусель N16,
  галерея G1, отзывы TS3, колесо F24, бегущая лента TS4.
- **Отметки и шаги** (`components/steps`): маркер, соединительная линия, состояния
  done/current/upcoming/error. Потребители: хронология C11, stepper F28, шаги агента A5,
  требования F3 (перевод без изменения вида).
- **Рамка графика** (`components/chart`, волна графиков): заголовок, легенда, серии через
  роли палитры и их прозрачности, текстовая альтернатива.
- **Слой эффектов** (последняя волна): `.tg-effect-layer` и загрузчик в `effects.mjs`.

### 4. Волны

Порядок — по зависимостям. Состав волны может уточняться в плане, но не порядок движков
перед потребителями. В скобках — существующие компоненты, которым нужен только пример
в каталоге или доводка до всех предложенных классов.

- **Волна 0. Основа.** Перестройка эталона; реестр и скрипт сверки; `data-spec` для уже
  готовых примеров; движки всплывающего слоя, строки-варианта, выбранного состояния и
  отметок; первые потребители — B15 подсказка и B8 сегменты.
- **Волна 1. Примитивы.** M15 kbd, M8 круговой прогресс, C11 хронология (+M10
  `--horizontal`), F28 пошаговая форма (+M9 `--vertical`), B9 группа и сплит-кнопка,
  B13 плавающая панель, B4 копирование, M3 регион toast, S2 разделитель с подписью,
  CT1 баннер, C2 медиа-карточка overlay, C17 раскрывающаяся карточка; доводка частично
  готовых P0 (D1, N1, F11 и др.); примеры (B17, M7, M19).
- **Волна 2. Выбор и ввод.** F8 listbox, F9 combobox, F10 теги, F14 карточки выбора,
  F4 число, F5 OTP, F18 двойной ползунок, F19 список загрузок, C5 hover-карточка,
  D3 панель фильтров; примеры (F1, F6, F7, F13, F16, F17).
- **Волна 3. Навигация и структура.** Движок дорожки; N16 карусель, G1 карусель
  изображений, N10 палитра команд, N11 боковая панель, N5 мега-меню, N3 вертикальные
  вкладки, N2 раскрывающиеся вкладки, N13 оглавление, N8 menubar; примеры (N6, N14).
- **Волна 4. Дата и время.** F20 поле даты, F21 календарь, F22 диапазоны.
- **Волна 5. Данные.** Рамка графика; D7 линии и области, D8 столбцы, D9 кольца,
  D6 сортируемый список, M11 расписание, C16 bento; примеры (D5, C12).
- **Волна 6. Ассистент, текст, карточки контента.** A5 шаги агента, A6 подтверждение,
  T1 редактор, T2 панель у выделения, TS1 карточка отзыва, PR2 карточка тарифа;
  примеры (B1, B3, B16).
- **Волна 7. Продвинутые P2.** B6 удержание и свайп, B12 плавающая кнопка, F24 колесо,
  F25 выбор цвета, F26 эмодзи, F33 холст и аудио, C15 стопка карточек, C21 плеер и
  сравнение, G4 аккордеон изображений, M22 затухание края, TS4 бегущая лента.
- **Волна 8. Эффекты.** Слой эффектов; B19, C18, F32, G2, SH1, SH2, SH3, SH4.

### 5. Каждая задача внутри волны

1. Классы в модуле-владельце или настройка движка; новые системные значения — в tokens.
2. Пример в каталоге с `data-spec`, правилом и HTML; поведение — в `docs/*.js`.
3. Браузерный тест по образцу `tests/workspace.browser.mjs`: геометрия от токенов,
   контраст ≥ 4.5:1 в трёх темах, клавиатура и ARIA, отсутствие горизонтальной
   прокрутки на 320/390/1440, RTL, reduced motion.
4. Строка реестра → `done`, галочка в плане.

### 6. Конец каждой волны

- Сборка, `npm test`, весь `npm run test:browser`, перестроенный тест эталона, скрипт
  сверки.
- Визуальная проверка новых примеров по craft floor impeccable и чек-листу Emil:
  скриншоты трёх тем на 320/390/1440, состояния (hover, focus, disabled, loading, error,
  empty), движение. Найденное исправляется до перехода к следующей волне.
- README: публичный API новых классов; DESIGN.md — только при изменении правил каталога.

### 7. Визуальное направление

- Компоненты (режим Operate): точность и сдержанность, знакомые паттерны, палитра из
  четырёх цветов, системный шрифт, плоские поверхности, тени только у плавающих слоёв.
  «Крутой визуал» достигается деталями: концентрические радиусы, точное выравнивание,
  табличные цифры, состояния, оформленные браузерные поверхности (выделение, каретка,
  фокус), продуманное движение.
- Эффекты (волна 8) — единственное место для выразительности сверх этого, всегда
  необязательные и с неподвижным вариантом.
- Движение: одно осмысленное на компонент, ease-out, 150–250 ms, выход быстрее входа,
  без анимации на клавиатурные действия.

## Уточнения после проверки

- **Каталог.** Шесть групп навигации DESIGN.md сохраняются: без секций лендингов новые
  разделы (дата и время, графики, ассистент и т. д.) раскладываются по смыслу в
  существующие группы. *Решение исполнителя.*
- **Где лежит учёт.** Спецификации уже в репозитории (`references/21st-dev-1000/`,
  закоммичены владельцем). Реестр `implementation.json` (110 спецификаций в работе; композиции перечислены отдельно со статусом `out-of-scope`) и скрипт сверки лежат в
  репозитории и читают пути относительно корня проекта.
- **Что считается готовым.** Спецификация `done`, когда реализованы все предложенные в
  ней классы или в README записано осознанное отклонение (например, класс не нужен,
  потому что это вид по умолчанию). Частично сделанные P0 (D1, N1, F11 и др.) в реестре
  стартуют как `todo` с перечнем недостающего и доводятся в волне 1. *Решение исполнителя.*
- **Тесты.** Отдельный браузерный тест обязателен для `new` и `extend`. Для `existing` и
  `composition` достаточно общего теста волны, который проверяет пример каталога по ID:
  присутствие, контраст текста в трёх темах, отсутствие горизонтальной прокрутки на
  320/390/1440 и имена у интерактивных элементов. Скрипт сверки принимает упоминание ID в
  любом тесте. *Решение исполнителя.*
- **Браузеры.** Итог должен проходить `npm run test:browser -- --webkit` на машине
  владельца; исполнитель проверяет в Chromium и пишет код с fallback: CSS anchor
  positioning — улучшение, базовое позиционирование через параметры хоста (как у меню);
  `@starting-style` — улучшение, без него элемент просто появляется. Поддержка: две
  последние версии Chrome, Safari и Firefox. *Решение исполнителя.*
- **Сложные виджеты и стандарт.** Абзац `docs/component-standard.md` о combobox,
  календаре, tree view и data grid обновляется: эти виджеты реализуются как CSS +
  ARIA-контракт, а полный клавиатурный контракт из спецификации показан в примере
  `docs/*.js` и покрыт тестом. Поведение демо — полное, не иллюстрация. *Решение исполнителя.*
