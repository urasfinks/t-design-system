# Спецификации компонентов по архиву 21st.dev

## Назначение

Превратить архив `references/21st-dev-1000/images/` в практические спецификации для дальнейшего развития T Design System. Документы должны помогать реализовывать компоненты в визуальном языке TDS, а не копировать чужой код или создавать 1000 несовместимых вариантов.

## Цели

- В каждой из 17 папок категорий создать `components.md`.
- Сгруппировать все 1000 превью в уникальные компоненты, варианты и композиции.
- Для каждой группы описать назначение, структуру HTML, предлагаемый публичный API `.tg-*`, модификаторы, состояния, адаптивность, поведение и доступность.
- Показать связь с существующей системой: переиспользовать, расширить, создать новый компонент или оставить композицией.
- Сохранить ссылки на все относящиеся к группе локальные изображения.
- Дать достаточную детализацию, чтобы по документам можно было составлять план реализации без повторного изучения всего архива.

## Не входит в задачу

- Реализация SCSS, JavaScript или новых компонентов.
- Изменение существующих публичных классов и визуальных контрактов.
- Пиксельное копирование превью 21st.dev.
- Перенос чужих палитр, шрифтов, декоративных эффектов и бизнес-логики.
- Добавление отдельного компонента для каждого незначительного визуального отличия.

## Ограничения и принципы TDS

- Системный шрифт, базовый текст 16 px, сетка отступов 4 px.
- Радиусы: карточки 16 px, кнопки и поля 12 px, внутренние контролы 8 px; капсулы только для chips, badges и switches либо явно обоснованных модификаторов.
- Только существующие семантические цветовые роли и четырёхцветная модель тем. Новых независимых палитр не предлагать.
- Плоские карточки по умолчанию; тени для выбранных сегментов и плавающих слоёв; glass только как опциональный материал.
- Touch target не менее 44 px; видимый keyboard focus; поддержка disabled, длинного содержимого, RTL и 200% текста там, где применимо.
- Анимации только через `transform` и `opacity`, общие duration/easing; обязательный reduced motion.
- Нативный HTML прежде custom widget. CSS не имитирует поведение, требующее состояния приложения или JS.
- У малого элемента рамка обозначает действие; статусы не становятся кнопками только из-за оформления.
- Публичные имена имеют префикс `.tg-*`; существующие классы сохраняются. Новые имена помечаются как предлагаемые.
- Документ разделяет ответственность TDS и приложения: стили и структура против данных, запросов, роутинга и бизнес-состояний.

## Рассмотренные подходы

1. Отдельная спецификация на каждое из 1000 превью. Даёт полный покомпонентный разбор, но создаёт повторы и раздувает будущий API.
2. Группировка в уникальные компоненты и паттерны с перечнем референсов. Сохраняет полное покрытие архива и формирует компактную реалистичную систему. **Выбран владельцем.**
3. Только отсутствующие компоненты. Короче, но теряет варианты расширения существующих компонентов и часть контекста референсов.

## Структура каждого `components.md`

1. **Название категории и назначение** — какие задачи решают референсы папки.
2. **Сводная таблица** — компонент/паттерн, тип работы (`existing`, `extend`, `new`, `composition`), количество референсов, приоритет (`P0`, `P1`, `P2`).
3. **Общие решения категории** — токены, геометрия, адаптивность и повторяющиеся правила.
4. **Спецификации компонентов** — от базовых примитивов к сложным композициям.
5. **Порядок реализации** — зависимости и рекомендуемые этапы без оценки сроков.
6. **Контрольный список покрытия** — соответствие групп и локальных файлов.

## Формат спецификации одного компонента

- Название и статус работы.
- Назначение: когда использовать и когда выбрать другой компонент.
- Состав: обязательные и необязательные области/элементы.
- Канонический HTML-каркас с существующими либо предлагаемыми `.tg-*` классами, label и ARIA.
- Публичный API: блок, элементы, модификаторы, локальные custom properties только для документированных измерений.
- Варианты из референсов: чем различаются и почему объединены либо разделены.
- Состояния: default, hover, focus-visible, active/selected, disabled, loading, empty, error — только релевантные.
- Поведение и ответственность приложения, включая клавиатурный контракт для интерактивных виджетов.
- Адаптивность: 320–1440 px, переполнение, длинный контент, мобильная компоновка.
- Доступность: нативные элементы, роли, имена, live regions, фокус, reduced motion.
- Токены и связь с существующими компонентами TDS.
- Критерии готовности и проверки.
- Список относительных имён всех изображений группы.

## Правила группировки

- Одинаковая задача и семантика важнее визуального сходства.
- Различия только в цвете, тени, иконках, содержимом и числе повторяющихся элементов остаются вариантами или данными примера.
- Новый компонент выделяется при новой семантике, клавиатурном контракте или существенно иной структуре.
- Маркетинговые секции, dashboards, testimonials и сложные экраны преимущественно описываются как композиции из примитивов TDS.
- Референсы с ошибочной исходной категорией учитываются по фактической семантике внутри текущего документа; файлы между папками не перемещаются.
- Каждый из 1000 файлов упоминается хотя бы один раз. Если файл объединяет несколько самостоятельных идей, допускается перекрёстная ссылка, но основная группа одна.

## Приоритеты

- `P0`: базовые примитивы и расширения, необходимые другим группам.
- `P1`: самостоятельные распространённые компоненты и композиции.
- `P2`: узкие, декоративные или ресурсоёмкие эффекты, не требуемые ядру.

Приоритет описывает порядок проектирования, не обещание реализации.

## Проверка результата

- Существует `components.md` в каждой из 17 папок.
- Все документы используют единый формат и учитывают существующий `docs/component-standard.md`.
- Все 1000 имён `.webp` из архива сопоставлены со спецификациями; отсутствующие и выдуманные имена недопустимы.
- HTML-каркасы согласованы с нативной семантикой и существующими классами TDS.
- Нет предложений создать отдельные цвета под конкретный референс или скопировать внешний стиль в ущерб системе.
- Для каждого интерактивного компонента явно описаны состояния, клавиатура и границы ответственности приложения.
